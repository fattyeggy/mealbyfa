## D1 · 按餐次下单 + 按营养素克数计价（DeepSeek，后端）

**为什么**：试运营只供午餐和晚餐，但现在的订单按「天」下，一天固定三餐，价格也是按「66 元 + 蛋白档位」算。

**设计（Claude）**

1. **允许的餐次由配置决定**：`meal.order.allowed-meals`（环境变量 `ORDER_ALLOWED_MEALS`），默认 `BREAKFAST,LUNCH,DINNER`。试运营设为 `LUNCH,DINNER`。
2. **默认餐次** = 用户建档时选的 `orderedMeals` ∩ 允许的餐次。交集为空时返回业务错误。
3. **订单**：只为选中的餐次生成 order item。
4. **计价：按营养素克数**（委托方 2026-11-24 决定）
   - 单餐价 = 蛋白g × 蛋白单价 + 碳水g × 碳水单价 + 脂肪g × 脂肪单价。
   - 克数用实际出品的克数，即 `ComponentPortioner` 算出的 plan item 的 `proteinG / carbG / fatG`。
   - 单餐价低于 `minMealPrice` 时按 `minMealPrice` 收；`minMealPrice` 为 0 时不生效。
   - 日应付 = 所选餐次单餐价之和，取整一次（HALF_UP），尾差放当天最后一餐。
   - 换菜补差保留（变动成本差 ÷ 0.77），加在克数价上。
   - 不再用基础价、餐次比例和 65 元最低日价。
   - 起始单价：蛋白 0.40 / 碳水 0.06 / 脂肪 0.10 元/g，`minMealPrice = 25`。
5. **定价版本**
   - 加字段 `pricingMode`：`MACRO_GRAM` 或 `PROTEIN_TIER`；
   - 加字段 `proteinPricePerG`、`carbPricePerG`、`fatPricePerG`、`minMealPrice`；
   - 旧版本标为 `PROTEIN_TIER`，已有订单按下单时的版本复现，不能重算。
6. 周券按日分摊、尾差放最后一天、锁单只核销一次：逻辑不变，基数换成新的日应付。
7. 缺口（`GapService`）、厨房汇总本来就按 order item 算，不用改。

**接口契约**（G1 按这个写，字段名不要改）

```
POST /app/orders/weekly/quote    请求加 mealTypes?: ("BREAKFAST"|"LUNCH"|"DINNER")[]
POST /app/orders/weekly          请求加 mealTypes?: 同上
  mealTypes 为空 → 用默认餐次

QuoteResp 增加：
  allowedMeals: string[]          // 配置允许的餐次
  defaultMeals: string[]          // 默认勾选的餐次
  mealTypes:    string[]          // 本次实际使用的餐次
DayQuote 增加：
  meals: [{ mealType, mealLabel, dishName, proteinG, carbG, fatG, price }]
  payableAmount                   // 当天应付（已扣券）

GET /app/plan/week 每个餐次 item 增加：
  price: number | null            // 该餐的克数价；不在 allowedMeals 里的为 null
  orderable: boolean
GET /app/orders/{id} 每个 item 增加：proteinG, carbG, fatG, price

后台定价版本（/admin/meal/pricing/...）增加：
  pricingMode, proteinPricePerG, carbPricePerG, fatPricePerG, minMealPrice
```

**红区**：`pricing`、`WeeklyOrderService`、`OrderService`、`PlanService`、表结构。只按上面的设计改。

**验收**

- 接口测试：
  - 只订午 + 晚：每天 2 个 item，日应付 = 两餐克数价之和（取整，尾差在晚餐）；
  - 配置 `LUNCH,DINNER` 时请求早餐：报错；
  - 单餐价低于最低价时按最低价收；
  - 周券分摊后各天应付之和 = 原价合计 − 券额；锁单只核销一次；
  - `PROTEIN_TIER` 旧版本下的订单金额不变。
- 原有测试全部通过。
- 提供新的 MySQL migration，并在工作说明里写执行顺序。

## G2 · 早餐自己吃的建议卡（Gemini，小程序首页）

**不依赖后端**，用现有接口：`GET /app/onboarding/gap`（`ordered`、`lines[].volumeText`）+ 当天订单。

**显示条件**：当天有订单，订单里没有早餐，且 `ordered=true`。

**结构**

- 标题：`早餐自己补这些`
- 三行缺口：直接用接口返回的 `volumeText`，只显示还差的项。
- 一句建议，按蛋白缺口分三档（文案已定稿，不改字）：

| 蛋白缺口 | 文案 |
| --- | --- |
| < 20g | `2 个鸡蛋 + 1 杯牛奶就够了` |
| 20–35g | `2 个鸡蛋 + 1 杯牛奶 + 1 个拳头大小的全麦面包` |
| > 35g | `3 个鸡蛋 + 1 杯无糖酸奶 + 1 个拳头大小的全麦面包，蛋白还不够就加一勺蛋白粉` |

**样式**：浅绿底 `#EEF3EE`，标题用主色，正文用次级色。位置在当天餐次列表下方。

**验收**：订了三餐、或当天没下单的用户看不到这张卡。在 D1 上线前，可以先用后台建一笔只有午餐和晚餐的订单来验证（找 DeepSeek 造数据）。附截图。

## D3 · 出餐核对（DeepSeek，后端）

**为什么**：下单时只自动拦截过敏原。忌口（`dislikes`）、饮食限制（`dietRestrictions`）和调料里的过敏原，要人在出餐前核对。

**设计**

- 新表 `meal_meal_check`：`order_item_id` 主键、`status`（`PENDING` / `OK` / `SWAP`）、`note`、`checked_by`、`checked_at`。
- 当用户的过敏、忌口、饮食限制任一项不为空时，这个 item 标为「需要核对」。
- 权限：运营和超级管理员可写，审计只读。

**接口契约**

```
GET /admin/meal/kitchen/checks?serviceDate=YYYY-MM-DD&batch=LUNCH|DINNER
  → [{ orderItemId, orderNo, contactName, mealLabel, dishName,
       needsCheck, userAllergies, userDislikes, userRestrictions,
       dishAllergens: string[], mainIngredients: string[],
       status, note, checkedBy, checkedAt }]
  需要核对的排在前面
PUT /admin/meal/kitchen/checks/{orderItemId}   { status: "OK"|"SWAP", note? }
标签接口（LabelRow）增加：needsCheck, checkStatus
```

**验收**：接口测试覆盖需要核对的识别、写入后读回、审计角色写入被拒；提供 migration。

## D5 · 体重记录（DeepSeek，后端）

**范围**：只记录，**不**自动改营养目标（重算规则是 C1）。

- 新表 `meal_weight_log`：
  - 字段：`id`、`user_id`、`log_date`、`weight_kg DECIMAL(5,1)`、`source`（`APP` / `ADMIN`）、`created_at`；
  - `(user_id, log_date)` 唯一。
- 校验：30–250kg。

**接口契约**

```
POST /app/weight            { weightKg }           // 当天重复提交就覆盖

                                 deltaKg | null, logs: [{logDate, weightKg}] }   // 按日期倒序
GET  /admin/meal/members/{id}/weight  → 同上
后台用户列表每行增加：latestWeightKg, weightDeltaKg
```

**验收**：接口测试覆盖覆盖写入、范围校验、只能看自己的记录；提供 migration。

## D6 · 部署 + 真机联调（DeepSeek + 委托方）

部署前完成三项：

- 云托管关闭「开放接口服务」，或设置 `WX_CA_CERT_PATH`；
- 设置 `CLAIM_SECRET`；
- 按顺序执行 migration。

然后按下面的顺序走，每一步记录结果。前端问题回给 Gemini，红区问题回给 Claude：

1. 新微信用户：登录 → 建档 → 生成计划。
2. 后台按手机号预建档案 → 用户用微信手机号授权认领 → 档案、余额、券都合并过来。
3. 手动输入手机号认领：不输认领码会被拦，输入正确的认领码后成功。
4. 发半价券 → 订一周午 + 晚 → 核对每天应付和券的分摊。
5. 厨房：生产汇总、出餐核对、标签打印。
6. 送达后完餐反馈。
