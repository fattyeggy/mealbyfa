# 发发的餐 · 开发说明（DeepSeek 后端 / Gemini 前端）

更新：2026-11-24　维护：Claude（架构 / 设计 / 评审）

## 0. 一句话

给有减脂 / 增肌目标的新乡用户，按个人营养目标配好每天的餐，按营养素克数计价、每天配送的订阅制餐饮。
**当前阶段**：试运营准备——5 人、一周、半价、**只供午餐 + 晚餐**（早餐给建议，用户自己吃）。按营养素克数计价。阶段二才接微信支付。

**流程**

1. Claude 在任务看板写卡。后端是 D 卡，前端是 G 卡，同一功能的两张卡共用一份「接口契约」。
2. DeepSeek 先做 D 卡。Gemini 只做「可开工」的 G 卡：不依赖后端的随时可以做，依赖后端的等对应 D 卡「通过」后再做。
3. 碰到卡上没写清的：**停下**，写进卡里的「待确认」，不要自己决定，也不要跨边界改别人的代码。
4. 做完跑第 6 节的检查，写工作说明，卡片状态改成「待评审」。
5. Claude 评审：看工作区 diff、工作说明和截图。
6. 评审通过后，DeepSeek 提交（前端改动也由它提交，提交信息里注明 G 卡号），然后按需部署。

**避免冲突**：DeepSeek 不改 `miniapp/`、`admin/`；Gemini 不改这两个目录以外的代码。两边都在同一个工作区里改，不执行 `git stash / reset / checkout` 这类会动到对方文件的命令。

**约定**

- 接口前缀：小程序 `/app/**`（会员 JWT），后台 `/admin/**`（后台 token + 角色）。
- 返回统一 `CommonResult`；业务错误抛 `ServiceException(ErrorCode.X)`。错误码按模块分段：1100 菜单、1200 建档、1300 钱包、1400 订单、1500 厨房、1600 反馈、1700 认领。新模块从 1800 起。
- 表结构：同一份 DDL 同时跑 H2 和 MySQL。新增列必须**同时**改 `schema.sql`（H2，测试用）和新建 `migration-<主题>-mysql.sql`（生产）。
- 测试：接口级测试放 `backend/src/test/java/.../<模块>/*ApiTest.java`，用 H2 起全量上下文。参考 `MemberClaimApiTest`、`CookRecordApiTest`。


## 4. 业务模型速览（改相关代码前必读）

### 4.1 营养目标（建档时算一次，不随菜单变）

```
BMR  = 10×体重 + 6.25×身高 − 5×年龄 + (男 +5 / 女 −161)
TDEE = BMR × 活动系数
热量 = TDEE − 400（减脂） / TDEE（维持） / TDEE + 300（增肌）
蛋白 = 体重 × 系数 × 食量系数
脂肪 = 热量 × 27% ÷ 9
碳水 = 余量
```

详细设计见 `docs/产品-营养模型与建档设计.md`。

**产品决定**：不做每餐比例，只保证**每天总量**够。三餐都在这里吃就保证达标；没订全三餐时，正式页面显示每种营养素还差多少，以及大概的食物体积。

### 4.2 份量（`ComponentPortioner`）

- 菜品 BOM 每行有组件类型：蛋白 / 主食 / 蔬菜 / 油脂 / 汤汁。按用户目标分别缩放各组件，不是整道菜等比放大。
- 单餐重量按**熟重**算：BOM 行有 `cooked_weight_g` 就用它，否则按「版本净重 ÷ 生重合计」折算。
- 没有组件营养数据的菜会回退成旧的等比缩放，计划页会出现 1000g+ 的大份，这不是样式问题。

### 4.3 缺口（`GapService`）

- 当天有有效订单：按订单的餐次算，`ordered=true`。
- 没有订单：按建档时选的餐次给预估，`ordered=false`。首页**只在 `ordered=true` 时**显示营养进度。
- 文案格式：`还差 32g，约 1 个掌心大小的瘦肉`。体积词由后端给（`volumeText`），前端不要自己拼。

### 4.4 计价

**新规则**（2026-11-24 决定，G1 实现）：按实际出品的营养素克数计价。

```
单餐价 = 蛋白g × 蛋白单价 + 碳水g × 碳水单价 + 脂肪g × 脂肪单价
日应付 = 所选餐次单餐价之和，取整一次
```

- 单价放在定价版本里（`pricingMode = MACRO_GRAM`）。
- 旧规则 `PROTEIN_TIER`（66 元含 60g 蛋白，每多 10g 加 1.90 元，最低 65 元）保留给旧版本和已有订单复现。
- 整周订单：周券按日分摊，尾差放最后一天，锁单时只核销一次。
- 蛋白目标超出 80–220g 不静默夹取，生成人工复核。

### 4.5 账号

- 微信登录 → openid。用微信手机号授权认领后台预建的档案（已验证，直接合并）。
- 手动输入手机号命中预建档案时，必须输入 6 位**认领码**（后台「会员建档」页显示，HMAC 生成，不落库）。

## 5. 设计规范（页面类任务必须遵守）

**颜色**（小程序和后台统一）

| 用途 | 值 |
| --- | --- |
| 主色 / 深墨绿 | `#032C0A`（后台 `--ink #1c3b2e`、`--green #1f5b40`） |
| 底色 / 米白 | `#F4F1E9` |
| 次级文字 | `#556A5E` |
| 浅绿底 | `#EEF3EE` |
| 强调 / 达标 | `#73C308` |
| 提示 / 琥珀 | `#875A1F`，底 `#fbf0e2` |
| 警告 / 超出 | `#B04A3A`（蛋白超出**不**标红） |

Logo 和头像在 `docs/品牌/`。

**文案**

- 用户看到的文字里不出现内部词：版本号、P1、点、定价版本、BOM、组件、复核门禁、个人主体。
- 营养用 `kcal` 和 `g`；体积用掌心、拳、汤匙。
- 价格显示**应付金额**（原价 − 券），不显示原价。
- 医疗相关只说「需遵医嘱」，不给建议。
- 星期按日期计算，不按数组下标。

**页面改动的交付**：H5 截图放 `docs/screenshots/<日期>-<任务号>/`，改前改后各一张。
