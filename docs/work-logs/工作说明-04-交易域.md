### 2.3 锁单事务

一次锁单在同一事务里完成五件事，任一步失败整体回滚：

```
行锁取单 → 状态校验 → 余额预检 → 扣款（写流水）→ 券核销 → 生成快照 → 创建两条配送 → 置为已锁定
```

**幂等靠三层，逐层都能独立挡住重复扣款**：

1. `SELECT ... FOR UPDATE` 行锁：并发线程串行化；
2. 状态机：非 `PENDING_LOCK` 直接跳过；
3. 账本唯一索引 `(biz_type, ref_type, ref_id, source)`：即使前两层被绕过，第二笔扣款也会插入失败。

### 2.4 账本不可删的代码级保证

`WalletLedgerMapper` **刻意不继承 `BaseMapper`**，只暴露 `insert` 与几个 `select` 方法。没有 update、没有 delete、实体也没有 `updater` 与逻辑删除字段——业务代码想改账本也没有入口。修正历史只能走 `reverse()`，生成一条 `REVERSE` 反向流水并通过 `reverse_of_id` 关联原流水。

### 2.5 资金分账与退款来源

- 账户同时维护 `balance / creditBalance / cashBalance`；
- 扣款时**赠送 credit 优先**，不足部分走现金；
- 退款按原 `ORDER_PAY` 流水的 `source` 逐笔反向生成 `REFUND`——赠送部分退回 `creditBalance`，不会变成现金；
- 同一订单同来源只能退一次（唯一索引兜底）。

### 2.6 订单唯一性

`meal_order` 用 `active_key TINYINT NULL` 表达「有效订单」：有效时为 1，取消或退款后置空。配合唯一索引 `(user_id, service_date, active_key)`，既保证「用户 + 服务日只有一张有效订单」，又允许取消后重新下单（MySQL 与 H2 的唯一索引都不约束 NULL）。

## 3. 关键决策与本轮新增假设

| 项 | 决策 | 说明 |
|---|---|---|
| 扣款顺序 | 先扣赠送 credit，再扣现金 | 保护用户现金余额；退款按来源回退，口径自洽 |
| 退款范围 | 仅支持下单后整单退款 | 部分退款、按餐次退款未做，第二阶段按需补 |
| 余额不足 | 只记失败原因，不抛异常回滚 | 若让扣款异常冒泡，Spring 会把整个事务标记回滚，失败原因会丢失 |
| 锁单触发 | 定时任务 + 后台手动补跑 | 手册要求定时；补跑用于联调与故障恢复 |
| 券使用时机 | 下单时校验，锁单时核销 | 锁单前取消可原路退回 |
| 配送记录 | 锁单时生成 BATCH_1 / BATCH_2 | 与「晚餐批次配送晚餐与次日早餐」一致 |
| 积分 | 未实现 | 手册写明第一阶段只记录不兑换，P4/P6 再补 |

### 4.3 本轮发现并修复的问题

| 问题 | 现象 | 处理 |
|---|---|---|
| 测试日期耦合 | 新用例按「今天+2 周」发布菜单，正好撞上旧用例的固定日期，导致旧用例误判「已发布」 | 旧用例固定日期迁到 2030 年，新用例按当前日期推算，两套日期不重叠 |
