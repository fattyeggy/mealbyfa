## 2. P0-1：高蛋白计划 500

**根因**：21 个餐次的复核原因拼成一条字符串写入 `review_note VARCHAR(255)`，142kg 以上触界餐次变多后必然超长。

**修复**：
- 新建 `meal_plan_review` 表，一条复核事项一行，类型为 `PROTEIN_RANGE / SCALE_CLAMP / PRICE_FLOOR / COST_MISSING / MANUAL`；
- `review_note` 改为 `TEXT`，只保留摘要，不再是事实来源；
- 计划上的 `needs_review` 降级为汇总冗余字段，响应中的 `needsReview` 以复核表为准（修复了「先查实体再写复核导致读旧值」的问题）。

**验证**：150kg 用户生成计划返回 `code=0`，`rawTarget=225.0g`、计划目标 `220g`、8 条复核事项完整保存。

---

## 3. P0-2：复核门禁真正生效

- 下单前依次检查：计划的 **PENDING** 复核事项、最新报价的复核标记、过敏原、成本；
- 任一存在即返回 `1208` 并附带具体原因，不扣款、不核销券、不生成快照、不产生生产记录；
- 新增后台处理接口 `GET /admin/meal/plans/{planId}/reviews` 与 `POST /admin/meal/reviews/{id}/resolve`；
- 复核状态按「类型 + 范围」精确替换：替换后只重估该餐次的 `SCALE_CLAMP` 与计划级 `PRICE_FLOOR`，不清空 `PROTEIN_RANGE` 等其他来源；
- 已 `RESOLVED` 的历史保留，计划重建时新计划重新生成复核事项（R06 验证）。

---

## 4. P0-3：蛋白目标不再静默夹取

| 项 | 之前 | 现在 |
|---|---|---|
| 计算器 | 夹在 80–220 | **不夹取**，返回原始值 |
| 计划服务 | 再夹一次 | 越界时按边界生成草稿 + 写 `PROTEIN_RANGE` 复核 |
| 响应 | 只有计划目标 | 同时返回 `rawTargetProteinG`（原始）与 `dailyProteinG`（计划） |

测试从「计价器单元测试」升级为 **`PUT /app/profile` → 生成计划 → 下单** 的完整链路（R01/R02/R07）。

### 5.3 本轮踩到的两个坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 改完仍返回 500 | 旧服务进程占着数据库，新进程启动失败，请求打到了旧实例 | 先 `pkill` 再启动；演练脚本执行前确认 `Started MealApplication` |
| 新表没生效 | `CREATE TABLE IF NOT EXISTS` 不会改已存在的表，本地 H2 文件仍是旧结构 | 开发环境删库重建；生产提供 `migration-p4.5-p4.6-mysql.sql` |
