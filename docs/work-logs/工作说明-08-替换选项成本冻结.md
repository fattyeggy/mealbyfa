## 1. 为什么单独做这一轮

P4.6 复盘时我把「替换选项未绑定成本版本」列为唯一仍影响价格正确性的缺口：审核通过的替换选项只记了「原菜品版本 → 替换菜品版本」和一个从未参与计算的 `costDelta`，无法说明审核当时依据的是哪套成本。

---

## 2. 完成内容

### 2.1 数据

`meal_pricing_version_swap` 新增三列：

| 字段 | 含义 |
|---|---|
| `from_version_cost` | 审核时冻结的原餐次标准份变动成本 |
| `to_version_cost` | 审核时冻结的替换餐次标准份变动成本 |
| `cost_frozen_time` | 冻结时间 |

`cost_delta` 保留为审计参考（= 两份标准成本之差），**不再参与任何计算**。

### 2.2 审核即冻结

`POST /admin/meal/pricing/versions/{id}/swaps` 现在会：

1. 读取原/替换菜品版本的标准份成本；
2. 任一侧成本缺失或 ≤ 0 → 直接拒绝（1208），不允许把「无成本」的替换审核成可售选项；
3. 写入两份冻结成本与冻结时间；
4. 只允许在 DRAFT 版本上追加，已发布版本需新建版本。

### 2.3 使用时按个人目标折算

存在已审核选项时，替换差价改用**冻结成本**计算：

```
个人份量成本 = 冻结标准成本 × (目标蛋白 ÷ 菜品蛋白)，比例夹在 0.5–2.0
替换差价     = (替换份量成本 − 原份量成本) ÷ 0.77
```

比例口径与实时缩放完全一致，因此：

- **不同蛋白目标会得到不同差价**（R10），不会用一个固定 `costDelta` 服务所有用户；
- 成本被重算（模拟成本版本更新）后，已审核选项的差价**不变**（R09）；
- 提交替换时把这份冻结成本写进 `plan_item.base_cost / cost`，后续每日报价沿用，BOM 再改动也影响不到。

## 3. 三层保护的关系

| 层级 | 保护对象 | 机制 |
|---|---|---|
| 1. 版本不可变 | 菜品成本本身 | 菜品版本创建即固化 `cost`，改价需新版本 |
| 2. 审核冻结 | 已审核替换选项 | 本轮的 `from/to_version_cost` |
| 3. 单据固化 | 已生成计划与已锁订单 | `plan_item` 存成本、订单明细复制、锁单快照 |

第 1 层原本就存在，但**无法覆盖成本重算任务直接改库**这类场景，也没有审计口径；第 2 层补上了这个缺口。
