# 工作说明 28 · 做菜记录（厨房手机端）

**日期**：2026-11-24
**依据**：委托方「需要一个记录做饭流程的工具，输出不同分量的热量，直接同步给后台」；在厨房用手机边做边记；分量按蛋白档位和成品克重都要，主菜要拆到出品时放多少肉、多少汤汁；步骤、火候时间、每步拍照都要。

## 用法

后台侧栏「做菜记录」，或手机直接打开 `后台地址/#/cook`（全屏手机页面，不套侧栏）。

1. **新建一锅**，填菜名。默认带 4 个出品组件：肉（主料）、汤汁、米饭（主食）、蔬菜。
2. **食材**：按组件加食材，称下锅前的**可食生重**。食材库里没有的可以现场新建；缺每 100g 营养的可以现场补。填这一锅分几份。
3. **步骤**：每步写做了什么，选火候，点计时（计时时屏幕常亮），拍照（自动压到长边 1280px 再上传）。
4. **出品**：做好后每个组件单独称**整锅熟重**（肉捞出来称、汤汁倒出来称）。标准一份默认 = 熟重 ÷ 份数，也可以单独填。页面显示出成率和每 100g 熟重营养。
5. **分量**：
   - 标准一份：每个组件放多少克、热量与三大营养；
   - 按蛋白档位（80/100/130/160/190g × 午/晚/早餐）：肉和汤汁一起按这一餐的蛋白目标放大缩小，主食、蔬菜按标准一份；
   - 按成品重量（默认 300/400/500/600g，可自己加）：整份按比例缩放。
6. **同步到后台**：选择或新建菜品，生成新的菜品版本（成品净重、营养、成本）和配方。旧的生效版本归档，已发布菜单不受影响。

全程自动保存（停手 0.9 秒）；保存前先备份在本机，网络断了也不丢，下次打开会提示恢复。「再做一锅」复制食材、组件、步骤，清空熟重和照片。

## 计算口径

- 组件营养 = 归到它的食材（生重 × 每 100g 营养）之和；每克熟重营养 = 组件营养 ÷ 熟重。
- 档位表：这一餐蛋白目标 = 档位 × 餐次占比（早 25% / 午 40% / 晚 35%，取自 `NutritionTargetCalculator`）；主料组（主料 + 汤汁）倍数 = (目标 − 其他组件蛋白) ÷ 主料组蛋白，限制在 0.30–2.50 倍（与 `ComponentPortioner` 一致），超出时标记。
- 每份营养按取整后的克数计算，厨房照着放与页面显示一致。
- 同步写入的配方 = 每样食材生重 × (该组件标准一份 ÷ 该组件熟重)，同一食材在不同组件分行。

## 后端改动

- 新增 `cook` 模块：`meal_cook_record`（内容 JSON）、`meal_cook_photo`（照片存库，云托管容器磁盘不持久）。
  接口 `/admin/meal/cook-records`：列表、详情、新建、保存（返回计算结果）、只计算、删除、复制、同步、照片上传/读取/删除。读用 `MENU_READ`，写用 `DISH_WRITE`。
- `meal_recipe_bom` 新增 `component_type`（可空），唯一键改为 `(dish_version_id, ingredient_id, component_type)`：
  - 配方行可以覆盖食材上的组件类型，新增 `SAUCE`（汤汁，跟主料一起缩放）；
  - 为空时完全沿用原逻辑（看食材的组件类型），已有菜品不受影响。
- `ComponentPortioner`：优先用配方行的组件类型；`SAUCE` 并入蛋白组件。缩放上下限常量改为 public 供做菜记录复用。
- `DishService.createVersion`：配方行可带 `componentType`，同一食材不同组件类型允许各一行；`DishDetailResp.BomLine` 返回 `componentType`。
- 上传大小：`spring.servlet.multipart` 单张 6MB（前端已压缩，服务端限制 5MB）。

## 部署

**生产 MySQL 必须先执行 `backend/src/main/resources/db/migration-cook-record-mysql.sql`，再部署新后端。**新代码查询配方时会读 `component_type`，不迁移会导致菜单、配餐、厨房页面报错。

本地 H2：`schema.sql` 只在新库里建表。已有的 `backend/data/` 库需要删掉重建，或在 H2 控制台手动执行迁移脚本里的 `ALTER TABLE`（H2 支持同样语法）。

## 验证

- 后端 137 项测试全部通过（原 126 项 + 新增 11 项）：
  - `CookCalculatorTest`：用可手算的批次核对出成率、每 100g 营养、标准一份（446g / 603 kcal）、160g 档午餐（肉 185g + 汤汁 49g）、80g 档早餐倍数限制、400g 克重表、同步配方生重与组件类型、阻止同步的情况；
  - `CookRecordApiTest`：新建 → 照片上传读取 → 保存与计算 → 拒绝引用别的记录的照片 → 同步 → 配方组件类型 → 配餐时汤汁跟主料放大（碳水 79.28g，若汤汁固定则只有 72.78g）→ 同步后再改回到未同步 → 复制 → 删除。
- 前端：本机没有 Linux 版 esbuild，无法跑 vite 构建；用 Vue 官方 SFC 编译器编译全部页面并做 TypeScript 检查，新增与改动文件无错误。
- 用 390×844 手机视口在 Chrome 里实际走完：新建 → 加 7 样食材称重 → 补营养 → 两步步骤（计时、拍照上传）→ 称熟重 → 分量表 → 选菜品同步 → 列表。后台生成第 1 版，配方 7 行组件类型正确。
- 未在真机和微信内置浏览器里试过；相机拍照依赖手机浏览器支持 `capture`。

## 发现但未处理（需确认）

- `ComponentPortioner` 返回的单餐重量是**配方生重之和 × 倍数**，不是熟重。米饭生熟差 2.5 倍，用户看到的份量克数和单餐重量上限都会偏离实际出品。做菜记录同步后版本的成品净重是熟重，但配餐时不用它。
- 后台类型检查中原有的问题：`Orders.vue` 引用未定义的 `batch`；`Pricing.vue` 的表单缺 `includedProteinG` 字段；`Catalog.vue` 第 894 行把字符串传给数字参数。
