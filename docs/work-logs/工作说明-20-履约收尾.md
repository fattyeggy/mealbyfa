## 1. 配送状态按单条更新

### 问题

`OrderService.updateDelivery` 按 `orderId + deliveryBatch` 批量更新，
完成 BATCH_2 时会把「11-18 早餐」和「11-19 晚餐」两条不同实际配送日的记录一起置为 DONE。

### 修复

- 接口改为按 `deliveryId` 更新：`POST /admin/meal/orders/{id}/delivery` 传 `{deliveryId, status}`；
- 服务层校验配送记录归属该订单，只更新一条；
- 完成时写 `deliverTime`，回退状态时清空；
- 订单详情返回 `id / actualDeliveryDate / deliverySlot`，后台配送列表按餐次逐行操作。

### 验证

真实接口（`scripts/verify-remediation.py`）：

```
完成晚餐只更新该条配送  {'LUNCH': 'PENDING', 'BREAKFAST': 'PENDING', 'DINNER': 'DONE'}
```

自动化用例 `deliveryStatusUpdatesOnlyTargetRow` 同时断言：非目标餐次状态仍为 `PENDING` 且没有送达时间。

## 2. 快照来源菜单边界

### 问题

锁单时按「用户 + 周起始日期」查计划取来源菜单。
若用户「下单 → 发布新菜单 → 重新生成计划 → 旧订单锁单」，旧订单会锁到新计划的菜单。

### 修复

- `meal_order` 增加 `source_menu_id` / `source_menu_version`，**下单时固化**；
- 锁单只读订单上的来源菜单；老订单没有该字段时才回退到计划，再回退到当周已发布菜单；
- `OrderSnapshotMapper` 不再继承 `BaseMapper`，只暴露 `insert / selectByOrderId / countByOrderId`，
  从数据访问层保证快照不可改。

### 验证

自动化用例 `snapshotUsesOrderSourceMenu` 严格按问题顺序执行：

1. 下单（记录旧菜单 id）；
2. 为同一周发布第二版菜单；
3. 重新生成个人计划（新计划指向新菜单）；
4. 对旧订单执行锁单；
5. 断言快照 `menuId` 等于下单时的旧菜单 id。
