## 1. 为什么先做这个

上一轮验收表里，这是唯一一条**业务链路之外的安全缺口**：任何后台账号都能发 credit、退款、改价。手册 §14 明确列了 8 个角色与禁止事项，而此前系统只有「登录 / 未登录」两种状态。

---

## 2. 按手册原文落地，而不是自己发明角色

从手册 §14 表格取出的 8 个角色与权限：

| 角色 | 可访问 | 禁止 |
|---|---|---|
| 超级管理员 | 全部 | — |
| 运营 | 菜单、用户、订单、券、credit | 不能改支付密钥 |
| 营养计划 | 档案、计划、菜谱营养 | 不能直接改余额 |
| 厨房负责人 | 生产、领料、分装、损耗 | 不看非必要身体数据 |
| 采购 | 食材与价格 | 不能改订单和余额 |
| 财务 | 支付、退款、账本、成本 | 不能改菜谱 |
| 配送 | 配送清单与状态 | 不看营养与财务 |
| 只读审计 | 日志、报表、历史版本 | 不能增删改 |

实现为 `Role` 枚举 → 权限点集合（20 个权限点，粒度到模块读写），接口通过 `@RequirePermission` 声明，`PermissionInterceptor` 在鉴权之后校验。

### 权限点与角色的关键取舍

- **发放 credit** 归运营与超管，**退款/冲正**归财务与超管——两者都是动钱，但职责不同，按手册分开；
- **定价发布**归财务与超管，**菜单发布**归运营/营养计划/超管——菜谱与价格分离；
- **审计读取**只有超管与只读审计——运营看不到审计日志（实测返回 403）。

### 4.2 真实服务实测

```
admin     role=['SUPER_ADMIN']
ops       role=['OPS']
finance   role=['FINANCE']
auditor   role=['AUDITOR']

ops 发 credit      : code 0
finance 发 credit  : 403 当前角色（财务）无权执行该操作
auditor 读审计     : 0
ops 读审计         : 403 当前角色（运营）无权执行该操作
admin 发 credit    : 0
```

后台顶栏同时显示「姓名 · 角色」，越权时前端直接弹出后端返回的具体原因。

### 4.3 本轮踩的坑

| 问题 | 原因 | 处理 |
|---|---|---|
| 所有接口返回 401 | 权限拦截器注册在鉴权之前，`UserContext` 还是空的 | 调换注册顺序，先鉴权后鉴权校验 |
| 既有 85 项测试大面积失败 | 测试里手工创建的 admin 没有角色，`Role.of(null)` 默认成运营 | 8 个测试类的账号初始化补 `SUPER_ADMIN` |
