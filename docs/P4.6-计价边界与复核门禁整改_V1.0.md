## 2. P0：高蛋白用户生成计划返回 500

### 2.1 实际复现

在独立服务中创建男性用户，使用正常活动量、维持目标和普通食量，修改体重生成计划：

- 100/110/120/130/140kg：本组场景可生成计划；
- 142/144/146/148/149/150kg：生成接口返回 `code=500`。

服务端实际异常：

```text
Value too long for column "review_note CHARACTER VARYING(255)"
at com.sancan.meal.plan.service.PlanService.generate(PlanService.java:187)
```

原因不是营养公式本身，而是多餐次复核原因拼接后写入 `meal_nutrition_plan.review_note VARCHAR(255)`，超过字段长度。

相关位置：

- `backend/src/main/resources/db/schema.sql`：`review_note` 定义；
- `backend/src/main/java/com/sancan/meal/plan/service/PlanService.java`：复核原因汇总及 `updateById()`。

### 2.2 修复要求

优先建立独立复核事项表，而不是简单截断文本：

```text
meal_plan_review
- id
- plan_id
- service_date
- meal_type
- review_type        PRICE_FLOOR / PROTEIN_RANGE / SCALE_CLAMP / COST_MISSING / MANUAL 等
- review_message
- status             PENDING / RESOLVED
- resolved_by
- resolved_time
- resolution_note
- creator/create_time/updater/update_time/deleted
```

要求：

1. 一个计划可保存任意数量复核事项，不能因字段长度导致计划生成失败。
2. `meal_nutrition_plan.needs_review` 可以作为汇总冗余字段，但不能成为唯一事实来源。
3. 计划重建时明确历史复核事项与旧计划的关联，不能覆盖已确认订单所需的审计历史。
4. 如果本轮暂不建表，最低限度也要把字段改为 TEXT 并保证完整保存；不得只截取前 255 字后丢弃原因。
5. 全局异常不得再把该场景包装成无信息的 500。

## 3. P0：计划的 needsReview 没有真正阻断下单

### 3.1 已确认的实现缺口

当前下单只检查：

```java
DailyPricingService.Quote quote = planService.dailyQuote(userId, serviceDate);
if (quote.needsReview()) { ... }
```

位置：`OrderService.java` 下单逻辑。

但未检查：

```java
NutritionPlanDO.getNeedsReview()
```

因此以下情况可能出现：

1. 计划生成时份量缩放触界，`plan.needsReview=1`；
2. 价格本身未触及最低价，蛋白也在范围内，`quote.needsReview=false`；
3. 下单只检查 quote，导致带未处理复核事项的计划仍可下单。

同时存在两个状态覆盖问题：

- `PlanService.applyReviewState()` 只用最新 quote 覆盖原计划的复核状态，可能清除生成阶段的份量触界原因；
- `applySwap()` 中替换后的 `scaled.clamped()` 未纳入新的复核状态。

### 3.2 修复要求

1. 下单必须同时检查：
   - 计划是否存在未处理复核事项；
   - `plan.needsReview` 汇总状态；
   - 最新报价新增的复核事项；
   - 过敏、成本及其他原有下单校验。
2. 复核原因必须合并，不能每次报价后把其他来源的复核原因清空。
3. 替换后必须重新评估份量触界、蛋白范围、成本和价格兜底，并保留仍有效的历史原因。
4. 已处理事项需要记录处理人、时间和说明；计划或替换再次变化时，应重新打开相关复核事项，而不是永久沿用旧审核。
5. 提供最小后台复核接口或在复核界面之前提供受控的管理员 API；不能只有 `needsReview` 标记而没有处理路径。

建议下单拒绝继续使用明确业务错误码和具体原因，例如：

```text
code=1208
msg=本单存在未处理复核事项，暂不能下单：2026-11-18 午餐份量超出允许范围
```

## 4. P0：蛋白目标仍被静默夹取，P11 未覆盖真实链路

### 4.1 问题

当前存在两层静默夹取：

- `NutritionTargetCalculator` 把蛋白夹在 80–220g；
- `PlanService.clampProtein()` 再次夹取。

这与工作说明06“计划蛋白超出范围时标记复核，不静默改蛋白目标”的表述不一致。

现有 `PricingRulesTest.p11ProteinOutOfRangeMarksReview` 只是直接调用：

```java
dailyPricingService.quote(version, 40, ...)
```

它能证明计价器会标记，却不能证明真实用户生成计划时也会标记。由于上游已夹取，越界值可能永远到不了计价器。

### 4.2 修复要求

采用以下统一口径：

1. 保留原始计算目标及取整后的目标，不得无痕改成边界值。
2. 超出 80–220g 时生成待复核草稿并标记 `PROTEIN_RANGE`，下单必须拒绝；也可以选择明确拒绝生成，但不能静默改成 80 或 220 后继续。
3. 计划响应同时返回原始目标、计划目标和复核原因，便于运营理解。
4. 增加从 `PUT /app/profile` → `POST /app/plan/generate` → `POST /app/orders` 的完整越界测试，不得只保留计价器单元测试。

## 5. P1：菜单蛋白上限与定价范围仍不一致

定价版本已支持 80–220g，但 `MealProperties.MenuCheck` 的默认菜单检查仍为：

```text
dailyProteinMaxG = 180
```

真实演示输出也仍显示“蛋白质 80–180g”。

处理要求：

1. 明确“公共标准菜单蛋白”和“个人计划蛋白”是否为两个不同口径。
2. 如果公共菜单也允许 220g，同步调整菜单检查及测试。
3. 如果标准菜单 intentionally 只支持 180g，则把配置名称、提示和文档改为 `standardMenuProteinMaxG`，并单独保留个人计划 80–220g 校验，避免运营误以为系统不支持 220g。
4. 不得只把 180 改成 220，而忽略热量、总重量、份量触界和人工复核。

## 6. P1：审核替换选项尚未真正绑定成本版本

### 6.1 当前问题

`meal_pricing_version_swap.costDelta` 当前只有写入，没有在计价计算中读取，也未绑定具体 BOM 成本版本。工作说明06已将其列为遗留。

此外：

```text
meal.pricing.allow-unreviewed-swap 默认 = true
```

这意味着当前默认配置仍允许未审核替换。

### 6.2 修复要求

1. 非测试环境默认：

```text
meal.pricing.allow-unreviewed-swap=false
```

只有明确的开发/测试 profile 才能放开。

2. 审核替换选项至少记录：
   - 原菜品版本与替换菜品版本；
   - 对应 BOM/成本版本；
   - 审核人、审核时间、状态；
   - 成本快照或可重算的成本依据。
3. 同一定价版本内，后台修改 BOM 或采购价不得悄然改变已确认计划及订单的替换价格。
4. 注意：**不能简单用一个固定 `costDelta` 服务所有用户**。不同蛋白目标和个人份量会导致替换成本差不同。应按用户计划目标和冻结成本版本重算，或者明确按蛋白目标区间配置差价。
5. 成本缺失、成本版本失效或选项未审核时，必须阻止提交，不得按零差价处理。

## 7. P1：定价版本发布需要参数校验和明确生效语义

当前 `PricingVersionService` 仍需补齐：

1. 草稿参数校验：
   - 基础价、加量单价、最低价不得为负；
   - 成本折算系数必须大于 0；
   - 蛋白最小值不得大于最大值；
   - 调整步长必须大于 0；
   - 早餐与午餐比例不得为负，且两者之和不得超过 1；
   - 三餐比例必须能完整分配日价。
2. 新版本发布前应有复核人及复核时间，不能仅创建后直接发布。
3. 本期如果只支持“立即生效”，明确 `effectiveAt=now`，发布即归档旧版本；不得通过 `active()` 的 fallback 提前使用未来版本。
4. 如果要支持未来生效版本，则当前生效版本必须在新版本生效前继续可用，不能发布未来版本时立即归档当前版本。
5. 没有已到生效时间的版本时，应返回明确业务错误，不能回退使用未来价格。

## 9. 实际接口验收要求

除了 JUnit，必须用独立数据库启动服务，至少执行以下链路：

```text
创建高蛋白用户
→ 提交 Onboarding
→ 生成计划
→ 确认返回 needsReview 及完整原因
→ 尝试下单
→ 验证明确拒绝且无扣款、无券核销、无快照、无生产记录
→ 后台完成或模拟完成复核
→ 再次修改计划并确认相关复核重新打开
```

另执行：

```text
创建未审核替换
→ 生产开关 false 下确认替换被拒绝
→ 审核替换并冻结成本版本
→ 修改 BOM/采购价
→ 验证历史计划和订单价格不变
```

验收时保留请求、响应和服务端日志，不得只引用测试类名称。
