## 0. 一句话

给有健身/减脂目标的城市用户，按**个人营养目标**配好每周三餐，按**营养点计价**、**每天两次冷链配送**、**按吃完反馈调整下一周**的订阅制餐饮服务。目前完成阶段一（内部 credit 体验）的可运行系统。

## 1. 商业逻辑

### 1.1 用户与痛点

| 用户 | 痛点 | 我们的解法 |
|---|---|---|
| 减脂/增肌的上班族 | 知道要吃多少蛋白，但不会配、没时间做 | 按目标算好每餐克重与营养点，直接送到 |
| 外卖党 | 油盐不可控、份量靠猜 | 每餐标注重量、蛋白、营养点，可追溯 |
| 想开始但怕坚持不了 | 不知道有没有效果 | 每餐反馈剩余与饱腹感，下周调整 |

### 1.2 产品形态

- **单档**：一个价格档位，不做多 SKU；
- **按周订阅**：每周一份菜单，7 天 × 三餐；
- **每天两次配送**：午餐一批；晚餐 + **次日早餐**一批（早餐随前一晚送到，冷食或短时复热）；
- **个人份量**：同一道菜，不同用户克重不同（按目标蛋白缩放）。

### 1.3 定价模型（计价规则 V1.0）

**日价**：

```
日价 = round( 66 + 1.90 × (目标蛋白g − 60) / 10 + Σ替换补差 )   最低 65 元
```

- 基础 66 元含 60g 蛋白；
- 每多 10g 蛋白加 1.90 元；
- 目标蛋白范围 80–220g，超出不静默夹取，生成复核；
- 三餐展示价只是日价拆分（早 25%、午 40%、晚取余），**不对单餐单独报价**。

**替换补差**：

```
补差 = (替换菜品变动成本 − 原菜品变动成本) ÷ 0.77
```

- 0.77 是「食材成本占售价」的系数，用于把成本差还原成售价差；
- **差价永远相对「最初默认餐次」**，A→B→A 必须回到原价；
- 替换选项需运营审核，审核时冻结成本，之后改采购价不影响已审选项。

**示例**（目标蛋白 100g）：

```
66 + 1.90 × (100−60)/10 = 66 + 7.6 = 73.6 → 74 元/天
```

### 1.4 成本与毛利（演示数据，真实采购价需替换）

| 项 | 单日示例 |
|---|---|
| 实收 | 80.00 |
| 食材 | 27.82 |
| 包装 | 6.00 |
| 配送 | 12.00（两次） |
| 支付手续费 | 0.48（0.6%） |
| 固定分摊 | 3.00 |
| 总成本 | 49.30 |
| 毛利 | 30.70（38.4%） |

三层成本口径：食材（BOM × 个人份量 ÷ 可食率 × 移动加权价）+ 包装/配送分摊 + 手续费/固定成本。

### 1.5 阶段规划

| 阶段 | 内容 | 状态 |
|---|---|---|
| 阶段一 | 内部体验：运营发放 credit，用户端显示「账户余额」，跑通菜单→计划→下单→锁单→生产→配送→反馈 | **已完成** |
| 阶段二 | 微信支付、退款回调、积分/优惠券对外 | 未开始（需商户资质） |

### 1.6 关键运营假设（待真实运营验证）

- 5 天 500 元 / 7 天 700 元的首批 credit（手册建议值）；
- credit 在内部体验期**不过期**；正式付费阶段另定规则；
- 目标：下单成功率 ≥95%、分装误差 ±5%、配送准时率 ≥90%、评分 ≥4.0。

## 2. 用户旅程与关键规则

### 2.1 首次进入（刚改完，待真机验证）

```
打开小程序 → 未建档：菜单 slide（出品图/菜名/克重/蛋白，可左右滑）
→ 开始定制 → 建档表单 → 提交 → 生成首周计划 → 首页
已建档 → 直接首页
```

- 建档状态存服务端（`onboardingStatus` / `onboardingTime`），启动时检查；
- 未建档不能进入首页、不能下单；
- 当前 slide 因缺少出品照片，使用设计过的渐变占位（有图片字段，上传后自动显示）。

### 2.2 计划生成

- 每天 3 餐，共 21 餐；
- 当前版本：先按身体数据算**目标蛋白**与热量，再按 25%/40%/35% 分到三餐，按每餐蛋白**缩放菜品份量**；
- **已知偏差**：碳水/脂肪没有固定目标，实际值随菜品波动（评审重点，见 §6.1）。

### 2.3 下单与锁单

- 服务日前一天 **12:00（北京时间）截止**下单；
- 锁单任务每日 12:00 执行，重复执行不重复扣款；
- 余额不足 → 锁单失败并记录原因，不扣款、不核销券；
- 一单一餐次唯一：同一用户同一服务日只能有一张有效订单。

### 2.4 优惠券

- 一单一张、不叠加；
- 下单时数据库条件更新**预占**（`RESERVED`），锁单时核销（`USED`），取消/退款只释放本订单的券；
- 并发使用同一张券只能成功一次；
- 券抵扣部分不产生积分。

### 2.5 账本（credit）

- 流水只增不改，冲正用反向记录；
- 退款按**原来源**退回（credit 回 credit、现金回现金）；
- 赠送 credit 不会退成现金。

### 2.6 生产与配送

- 生产日 D：D 日午餐 + D 日晚餐 + **D+1 日早餐**；
- 配送：午餐批次（D 日）、晚餐及次日早餐批次（晚餐 D 日送、早餐 D−1 日晚送）；
- 每条配送记录有 `serviceDate`（餐次属于哪天）与 `actualDeliveryDate`（实际哪天送）；
- 配送状态**按单条记录**更新，完成晚餐不会误把次日早餐也标记完成。

### 2.7 快照（历史订单不可变）

- 下单时把菜单来源固化在订单上；
- 锁单生成快照：菜品版本、BOM、营养、过敏原、保存/复热、成本、定价明细；
- 快照只插入，不更新、不删除；
- 之后改菜单、改价、改 BOM，历史订单内容与金额不变。

### 2.8 复核门禁

出现以下情况生成「复核事项」，未处理时不能下单：

- 目标蛋白超出 80–220g；
- 餐次缩放超出 0.5–2.0 倍；
- 日价触发最低价 65 元。

## 3. 技术架构

### 3.1 组成

| 模块 | 技术 | 说明 |
|---|---|---|
| 后端 | Java 17 + Spring Boot 3.3.5 + MyBatis-Plus | 88 个接口、30 张表 |
| 小程序 | UniApp（Vue3 + TS） | 5 个页面，H5 与微信小程序双构建 |
| 运营后台 | Vue3 + Element Plus | 11 个页面（菜单、复核、定价、订单、厨房、成本、用户、反馈、审计等） |
| 数据库 | 开发/测试 H2（MySQL 模式）；生产 MySQL 8 | 单份可移植 `schema.sql` + 增量迁移 |
| 部署 | 单 jar + 静态前端 | 见 `docs/交付/部署手册.md` |

### 3.2 与 RuoYi 的差异（评审需知）

交接手册要求基于 RuoYi-Vue-Pro 单体，但当前环境没有 MySQL/Redis/Docker，RuoYi 无法启动验证，因此交付为**独立可运行的 meal 服务**，按 RuoYi 约定组织（包结构、`CommonResult`、Bearer 鉴权、审计字段、权限点命名），保留后续并入 RuoYi 的适配点。

### 3.3 权限

8 个后台角色：超级管理员、运营、营养计划、厨房、采购、财务、配送、只读审计；接口级权限注解 + 拦截器，越权返回 403。

## 6. 已知问题与风险（请重点看）

### 6.1 营养模型（最大的产品偏差）

- **现状**：蛋白目标固定，但碳水/脂肪没有目标；每餐按蛋白缩放，热量/碳水/脂肪随菜品波动；
- **应改为**：先固定每日三大营养素与热量目标，再分到每餐，菜单只负责「吃什么」；
- **设计已出**（`docs/产品-营养模型与建档设计.md`），默认参数待确认：脂肪 27%、三餐 25/40/35、偏差只提示 + 复核。

## 8. 希望评审重点回答的问题

1. 营养模型的改法是否成立？「固定三大营养素 → 每餐目标 → 菜单适配」在只有单档、单菜品的约束下是否可行？
2. 计价公式（66 + 1.9/10g + 补差/0.77）在连续替换、冻结成本、最低价兜底之间是否存在套利或漏洞？
3. 一券一次、锁单幂等、退款按来源这三条资金规则是否还有边界情况？
4. 快照「只插入」是否足以支撑「历史订单不可变」？还缺什么（例如菜品版本本身可变）?
5. 跨日配送模型（早餐随前晚）是否会与「服务日截止下单」冲突？
6. 单档 + 每周菜单的产品结构，是否支持后续做多档位/自选？
7. 阶段一用 credit 代替支付，是否存在被用户理解为「储值」的合规风险？
8. 运营后台的角色权限划分是否合理？财务与运营的边界是否需要调整？
9. 111 项测试的覆盖是否有明显盲区（尤其是并发、金额、跨日）？
10. 与 RuoYi 的差异是否会影响后续交接与二次开发？
