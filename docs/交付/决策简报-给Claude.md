## 1. 项目一句话

给有减脂/增肌目标的城市用户，按个人营养目标配好每周三餐，按营养点计价、每天两次配送、按吃完反馈调整下一周的订阅制餐饮服务。

当前处于**阶段一：内部体验**（运营发 credit，用户端显示「账户余额」），阶段二才接微信支付。

## 2. 商业逻辑（事实）

### 2.1 产品形态

- 单档定价，不做多 SKU；
- 按周订阅：每周一份菜单，7 天 × 三餐；
- 每天两次配送：午餐一批；晚餐 + **次日早餐**一批；
- 同一道菜按用户目标蛋白缩放份量（个人克重不同）。

### 2.2 计价（已实现，V1.0）

```
日价 = round(66 + 1.90 × (目标蛋白g − 60)/10 + Σ替换补差)，最低 65 元
替换补差 = (替换菜品变动成本 − 原菜品变动成本) ÷ 0.77
```

- 基础 66 元含 60g 蛋白；每多 10g 加 1.90 元；
- 蛋白范围 80–220g，超出不静默夹取，生成人工复核；
- 三餐展示价是日价拆分（早 25%、午 40%、晚取余），不单独报价；
- 替换补差永远相对「最初默认餐次」，A→B→A 必须回到原价。

### 2.3 成本与毛利（演示数据）

| 项 | 单日示例 |
|---|---|
| 实收 | 80.00 |
| 食材 | 27.82 |
| 包装 | 6.00 |
| 配送 | 12.00（两次） |
| 手续费 | 0.48 |
| 固定分摊 | 3.00 |
| 总成本 | 49.30 |
| 毛利 | 30.70（38.4%） |

|---|---|---|
| 阶段一 | 内部 credit 体验，跑通全链路 | 基本完成 |

## 3. 当前操作流程（事实）

```
打开小程序
 → 未建档：菜单 slide（菜名/克重/蛋白，可滑动）
 → 开始定制 → 建档（身体/目标/食量/过敏/配送）
 → 生成首周计划 → 首页
 → 选择某一天 → 查看三餐 → 下单（填地址、选券）
 → 服务日前一天 12:00 锁单扣款
 → 厨房生产 → 两次配送 → 用户收餐 → 完餐反馈 → 周复盘
```

**已知问题**：当前是**按天单独下单**，而产品对外是**每周订阅**；首页已显示「已订 X/7 天」，但没有一键订整周。

## 4. 计算模型（事实 + 已知偏差）

### 4.1 现在怎么算

- 基础代谢 Mifflin-St Jeor × 活动系数 → 每日热量（减脂 −400 / 增肌 +300）；
- 每日蛋白 = 体重 ×（减脂 1.8 / 维持 1.5 / 增肌 1.8）× 食量系数；
- 三餐按 25% / 40% / 35% 分蛋白；
- 每餐按目标蛋白**缩放菜品份量**；
- **碳水、脂肪没有目标**，实际值由菜品决定。

### 4.2 委托方认为应该是

先固定客户的**三大营养素 + 热量**需求 → 分到每餐目标 → 再让菜单去适配；菜单只是「吃什么」的载体，不决定需求。

### 4.3 已有设计草案（未实施）

```
热量 = BMR × 活动系数 ± 目标调整
蛋白 = 体重 × 1.5~1.8 × 食量系数
脂肪 = 热量 × 27% ÷ 9
碳水 = (热量 − 蛋白×4 − 脂肪×9) ÷ 4
三餐分配 25/40/35；偏差阈值：蛋白±5%、热量±10%、碳水±15%、脂肪±20%
```

超阈值处理三选一：只提示 + 复核 / 自动调份量（会改价）/ 加配菜（需新商品）。

## 6. 需要 Claude 决策的问题

### D1. 下单模型

- A. 一键订整周（生成 7 张日订单，合计金额一次确认）
- B. 保持按天订，但交互上说明「选择日期预订」
- C. 真正的周订单（一次扣款，后台按天拆生产）

现有订单/锁单/快照都是按「服务日」设计的。请给出：选哪个、优惠券在整周场景怎么处理、对锁单与退款的影响。

### D2. 营养模型

是否改为「固定三大营养素 → 每餐目标 → 菜单适配」？请给出：
- 脂肪比例（25/27/30%）；
- 三餐热量分配（25/40/35 或其他）；
- 超阈值处理（提示 / 调份量 / 加配菜）；
- 只有单档、每天只有一道固定菜品的约束下，这套模型是否成立，是否需要允许「配菜/加餐」。

### D3. 定价模型

66 + 1.9/10g + 补差/0.77 是否延续到阶段二？替换补差用 0.77 系数是否合理？是否需要按菜品成本率动态调整？

### D4. 履约模型

午餐一批、晚餐+次日早餐一批；服务日前一天 12:00 截止。这个模型是否可持续（配送成本、早餐体验、跨日归属）？是否需要改成一天一配或隔日配？

### D5. Onboarding 范围

首次进入是否强制建档（当前是）？建档字段建议保留哪些、删减哪些？是否允许访客只看 slide 不看完整菜单？健康声明（孕期/慢病）怎么处理？

### D6. 进度与阶段划分

阶段一收尾标准是什么？阶段二先做支付还是先做「周订阅改造」？哪些增强项（地址簿、菜品图、字段脱敏、状态时间线）应该排在支付前？

### D7. 技术框架

继续独立 meal 服务，还是尽快并入 RuoYi-Vue-Pro 单体？并入的时机与代价？给一个判断标准。

### D8. 人工与自动的边界

### D9. credit 与正式付费的过渡

内部体验 credit 不过期；正式收费后，老用户体验 credit 怎么处理（继续有效/限期用完/转优惠券）？

### D10. 成功指标
