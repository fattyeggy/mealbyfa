# 三餐私教计价规则与开发验收 V1.0

**日期**：2026-11-15  
**状态**：开发与内部体验基线  
**适用阶段**：P4.5 计价整改，以及后续小范围付费前的定价验收  
**适用范围**：用户按服务日购买早餐、午餐、晚餐的个性化营养三餐  

> 本文件用于统一业务、产品、开发和测试口径。开发团队不得再从 UI 示意图反推售价，不得把演示参数当作已确认的经营规则。真实收费前仍需用实测 BOM、配送成本和付费数据校准参数；调整参数必须产生新的定价版本，不能修改已确认或已锁定订单。

---

## 1. 一句话计价模型

本项目采用类似称重快餐的透明加价逻辑，但不按全天食物总重量乘统一单价：

> **每日到手价 = 基础三餐费 + 蛋白加量费 + 蛋白来源/菜品替换差价 − 优惠券。**

核心规则：

1. 基础三餐费 **66 元/服务日**，包含三餐、基础 60g 计划蛋白、标准包装及标准配送范围内的两次配送。
2. 计划蛋白超过 60g 的部分，每 **10g 加收 1.90 元**，不足 10g 按比例计算。
3. 蛋白目标支持 **80–220g/日**。系统生成目标可为整数克；用户手动调整以 ±10g 为步长。
4. 日价以元为单位四舍五入，最低日价 **65 元**。
5. 替换蛋白来源或菜品时，固定成本不重复计算，只按同一口径的变动成本差计算补价或减价。
6. 售价按服务日确定。三餐展示价只是日价拆分，不是三个独立商品报价。

---

## 2. 为什么不是普通“按总重量称重”

普通称重快餐通常按成品重量收费。本项目虽然也按份量变化计价，但蔬菜、主食、肉类和乳制品的单位重量成本、蛋白质含量差异很大，不能采用“全天总克重 × 一个单价”。

本项目采用三类价格信号：

| 组成 | 类比称重快餐 | 本项目规则 |
|---|---|---|
| 基础三餐 | 餐盒、基础配菜和基础服务 | 66 元，含基础 60g 计划蛋白 |
| 蛋白加量 | 主菜多加、多称多付 | 超出 60g 的部分每 10g 加 1.90 元 |
| 来源替换 | 不同荤菜价格不同 | 按替换前后变动成本差补价或减价 |

“全天食物总重量”用于向用户展示份量和履约，不参与统一乘价。“计划蛋白”用于计价，“实际熟重”用于生产和分装，两者不得混用。

## 3. 术语与计算口径

| 术语 | 定义 |
|---|---|
| `P` | 用户某服务日的计划蛋白目标，单位为 g；取整数，范围 80–220 |
| 营养点 | `P ÷ 10`；仅用于解释蛋白计划，不是货币，也不是消费积分 |
| 基础蛋白 | 基础日价已经包含的 60g 计划蛋白 |
| 加量蛋白 | `max(0, P − 60)` |
| 参考日价 | 未发生蛋白来源/菜品替换、未使用优惠券时的日价 |
| 替换差价 | 替换前后同一餐次变动成本差，按 0.77 折算后的金额；可正可负 |
| 到手日价 | 参考日价加替换差价、完成日价取整后的金额 |
| 实付金额 | 到手日价扣除优惠券后的金额；钱包 credit 和现金是支付方式，不改变标价 |

营养计算中的实际出品蛋白可能因食材和熟重取整出现小数。若计划无法达到目标，必须进入人工复核，不得通过静默改变蛋白目标或价格来掩盖偏差。

## 4. 参考日价公式

无替换时，未取整价格为：

```text
rawReferencePrice = 66 + 1.90 × (P − 60) ÷ 10
```

最终参考日价：

```text
referencePrice = max(65, roundHalfUp(rawReferencePrice, 0 decimal places))
```

计算要求：

- 使用 `BigDecimal`，禁止使用 `float` 或 `double` 计算金额。
- 先按完整日计划计算，再对日价取整。
- 不得分别计算三餐营养点和价格后再产生额外舍入差。
- 不得使用当前 `point_unit_price = 5`、`base_price.BREAKFAST/LUNCH/DINNER` 作为正式售价参数。

### 4.1 标准验收购价表

| 计划蛋白 P | 营养点 | 未取整价格 | 参考日价 |
|---:|---:|---:|---:|
| 80g | 8.0 | 69.80 | **70 元** |
| 100g | 10.0 | 73.60 | **74 元** |
| 120g | 12.0 | 77.40 | **77 元** |
| 135g | 13.5 | 80.25 | **80 元** |
| 150g | 15.0 | 83.10 | **83 元** |
| 180g | 18.0 | 88.80 | **89 元** |

## 5. 三餐展示价拆分

三餐不独立定价。界面需要展示每餐价格时，按以下比例拆分到分：

```text
早餐展示价 = roundHalfUp(到手日价 × 25%, 2 decimal places)
午餐展示价 = roundHalfUp(到手日价 × 40%, 2 decimal places)
晚餐展示价 = 到手日价 − 早餐展示价 − 午餐展示价
```

晚餐采用余额法，确保三餐之和始终等于到手日价。

示例：

| 到手日价 | 早餐 | 午餐 | 晚餐 | 合计校验 |
|---:|---:|---:|---:|---:|
| 77 元 | 19.25 | 30.80 | 26.95 | 77.00 |
| 83 元 | 20.75 | 33.20 | 29.05 | 83.00 |

该拆分只用于展示和内部成本分析。第一阶段不据此开放单餐退款、单餐独立优惠券或单餐单独售卖。

## 6. 蛋白来源与菜品替换差价

### 6.1 原则

1. 同一蛋白目标下，默认蛋白组合不额外加价。
2. 更换蛋白来源或菜品时，只计算变动成本差，不重复计算基础餐费、房租、人工分摊和标准配送费。
3. 贵价替换应补价，便宜替换应减价，保持透明。
4. 不得再用统一的 `protein_swap_surcharge` 代表所有食材替换。
5. 缺少有效成本数据时必须返回“待定价/待人工复核”，不得默认差价为 0。

### 6.2 公式

对发生替换的每个餐次：

```text
rawSwapDifference = (replacementMealVariableCost − originalMealVariableCost) ÷ 0.77
```

一天内所有替换合并后，只进行一次日价取整：

```text
rawAdjustedPrice = 66 + 1.90 × (P − 60) ÷ 10 + Σ rawSwapDifference
adjustedDailyPrice = max(65, roundHalfUp(rawAdjustedPrice, 0 decimal places))
```

成本口径必须一致：

- 原餐次和替换餐次均按同一计划蛋白目标、同一可食生重/熟重口径计算；
- 变动成本包含食材和随份量变化的成本；
- 固定成本和不因替换变化的成本不参与差价；
- 若替换整道菜，应比较整道菜的变动成本，不能只比较其中一种肉类；
- 0.77 沿用 V10 的成本折算系数，不代表最终净利润率。

### 6.3 示例

假设原餐次变动成本为 20 元，替换餐次为 26 元：

```text
rawSwapDifference = (26 − 20) ÷ 0.77 = 7.792207…
150g 计划：rawAdjustedPrice = 83.10 + 7.792207… = 90.892207…
最终到手日价 = 91 元
```

便宜替换采用同一公式计算负差价，不得只支持加价、不支持减价。

### 6.4 第一阶段开放边界

自由替换功能由配置开关控制。在 BOM、成本和营养数据未经运营复核前：

- 可以保留试算接口和测试；
- 不向真实用户开放任意菜品替换；
- 只开放少量已经定价并审核的替换选项；
- 成本缺失、版本失效或营养复核未通过时禁止提交。

## 7. 优惠券与实付金额

计算顺序固定为：

```text
蛋白目标与替换方案
→ 计算并取整到手日价
→ 校验并应用一张优惠券
→ 得出订单实付金额
→ 选择 credit、现金或后续微信支付
```

公式：

```text
payableAmount = max(0, adjustedDailyPrice − couponDiscount)
```

规则：

- 每个服务日订单最多使用一张券，不叠加。
- 优惠券属于营销优惠，不回写基础定价规则。
- 钱包 credit、现金余额和微信支付是资金来源，不改变订单标价。
- 退款、积分和财务报表均以实际订单来源及实付净额为准，相关细则由交易域文档另行统一。

---

## 8. 定价版本与订单价格稳定性

当前键值表直接覆盖参数、即时影响所有新计划的方案不足以支持审计，必须改为定价版本机制。

每次变更至少保存：

| 字段 | 要求 |
|---|---|
| `pricing_version` | 唯一版本号，发布后不可修改 |
| `status` | DRAFT / PUBLISHED / ARCHIVED |
| `effective_at` | 生效时间 |
| 基础价、基础蛋白、加量单价、最低价 | 本版本完整参数 |
| 成本折算系数 | 当前为 0.77 |
| 蛋白目标范围和调整步长 | 当前为 80–220g、±10g |
| 替换选项及成本版本 | 可追溯至菜谱 BOM 与成本版本 |
| 创建人、复核人、发布时间 | 必须留痕 |

订单规则：

1. 用户确认方案时保存 `pricing_version` 和完整价格明细。
2. 锁单前调整蛋白或替换来源，仍使用该订单已确认的定价版本重新试算，并要求用户确认新价格。
3. 已确认但未锁定的订单，不因后台发布新价格而被动改价；取消后重新下单才使用新版本。
4. 锁单后保存不可变价格快照，后台改价、改 BOM 或改菜单不得改变历史订单。
5. 新计划使用当前生效版本；历史计划仍可解释其当时的计算依据。

## 9. 用户端展示规则

用户端优先展示：

```text
今日计划蛋白：150g
基础三餐：66 元，含 60g 基础蛋白
蛋白加量：90g，加 17.10 元
日价取整：83 元
替换补差：如有则单独展示
优惠券：如有则单独展示
实付金额：最终金额
```

展示要求：

- 明确“1 营养点约等于 10g 计划蛋白”，不得与现金积分混淆。
- 总食物重量、各餐熟重用于展示份量，不显示为“总重量 × 单价”。
- 替换补价或减价必须在确认前展示，不能锁单后才发现。
- 不用“毛利 24%”等内部经营指标面向用户宣传。
- 示意图中的 78 元、18/32/28 元等仅作视觉示例，不作为计算验收数据。

## 10. 对现有实现的整改要求

### 10.1 停用现有错误或非正式口径

以下参数不得继续作为正式计价基线：

```text
point_unit_price = 5
base_price.BREAKFAST = 4
base_price.LUNCH = 11
base_price.DINNER = 5.5
protein_swap_surcharge = 0
```

现有 P2–P4 演示价格、周总价、成本率和毛利可作为流程演示保留，但不得再作为定价正确性或经营可行性的验收证据。

### 10.2 新基线参数

```text
daily_base_price = 66.00
included_protein_g = 60
extra_protein_price_per_10g = 1.90
min_daily_price = 65.00
min_target_protein_g = 80
max_target_protein_g = 220
manual_protein_adjust_step_g = 10
swap_cost_divisor = 0.77
daily_price_rounding = HALF_UP_TO_INTEGER_YUAN
meal_display_ratio = BREAKFAST:0.25,LUNCH:0.40,DINNER:0.35
```

这些参数仍需版本化。不得仅把旧默认值替换成另一组可即时覆盖、无历史版本的键值。

### 10.3 接口返回

计划试算和订单确认至少返回：

- 定价版本；
- 计划蛋白、基础蛋白、加量蛋白；
- 基础日价和加量费；
- 每个替换的成本差、折算差价及成本版本；
- 取整前日价、到手日价；
- 三餐展示价；
- 优惠券和实付金额；
- 是否存在待人工复核事项。

不得向用户端暴露不必要的采购成本、供应商或内部利润信息；后台应保留完整审计明细。

## 12. 上线前业务验收

真实收费前必须同时满足：

1. 标准验收购价表全部通过，三餐拆分无尾差。
2. 至少完成一周菜单的 BOM、可食率、熟重、营养和成本复核。
3. 默认蛋白组合和每个开放替换选项均有已审核成本版本。
4. 包装、两次配送、支付手续费和固定成本使用经营方确认的口径，不使用 P4 演示的固定 3 元/单证明利润。
5. 实测食材与配送成本后，由经营方决定保留当前参数还是发布新定价版本。
6. 内部 credit 体验与真实付费验证分开报告，不能用赠送余额消耗率代替真实购买率。
7. 所有已确认和已锁定订单均能解释价格来源，并不受后续改价影响。

---

## 13. 本期明确不做

- 不按全天食物总重量乘统一单价。
- 不对三餐分别设置互相独立的基础价和营养点单价。
- 不允许开发团队用示意图价格反推经营参数。
- 不允许统一“替换 surcharge”替代真实成本差。
- 不允许成本缺失时默认免费替换。
- 不在本文件中展开单餐退款、复杂促销、积分兑换和动态竞价；这些功能不得反向破坏本计价基线。
